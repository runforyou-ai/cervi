# AI 客服回答质量评测方案

状态：第二阶段待实施
日期：2026-09-29
范围：评测用例的待补知识与问题会话入口
关联：本文是 [Luway 路线图](roadmap.md)「满意度与质检」中「回答质量评测」的独立方案

评测针对已生效的配置，定位是改动后的质量检查；发布前验证需要配置草稿与发布，在出现「改动先验证再上线」的需求时另行评估。评测结果决定是否为 AI 客服增加「依据范围校验」。

## 1. 用例入口

| 入口 | 位置 | 内容 |
| --- | --- | --- |
| 待补知识 | 采纳待补知识的表单中「同时加入评测」，默认勾选；没有提问消息的待补知识不显示该勾选项 | 用例归属登记时负责的 AI 员工；前文截止到待补知识的提问消息；提问取该消息；期望处理方式为 `reply`；标准答案取采纳时保存的问答答案。质检判定答错的周期已登记为待补知识，答错类用例只从这里加入 |
| 问题会话 | AI 表现「问题会话」中「应转人工未转」会话的「加入评测」 | 提问默认取周期内最后一条客户文本，负责人可在沟通记录中改选应当转人工的那条客户消息；前文为所选消息之前的全部往来；期望处理方式固定为 `handoff`，无需填写标准答案 |

两个入口的提问人都是客户。

## 2. 数据模型

第二阶段作为独立 PR，在第一阶段合入 `main` 后以增量迁移为 `agent_evaluation_cases` 追加：

| 字段 | 含义 |
| --- | --- |
| `source` | 来源：`manual` 手动、`knowledge_gap` 待补知识、`service_session` 问题会话；已有用例为 `manual` |
| `service_session_id` | 来源服务周期编号，手动用例为空 |
| `occurred_at` | 所选提问消息的时间，手动用例为空 |
| `context` | 加入时的快照，见第 3 节；手动用例为空 |

运行冻结的用例快照同时带上前文、客户上下文与客户身份，单条重跑沿用快照。

## 3. 快照

加入时写入用例的 `context`，不引用原会话，原会话后续变化或删除不影响用例：

- 前文：发送方为 `customer`（客户）、`ai`（AI 员工）或 `staff`（真人处理人）及正文，单条截断规则与质检沟通记录一致；首期只保存文本，附件以文件名占位。回放时客户消息为用户角色，AI 与真人消息为助手角色。
- 客户上下文：生成当时的客户上下文消息正文（身份、访问信息、客户档案与历史小结），回放时作为第一条消息，与客服运行开头的上下文消息一致。
- 客户已验证身份：企业用户编号与邮箱，回放时供按客户查询的 MCP 服务使用；未验证时为空，按客户查询的服务不挂载。

## 4. 回放中的客户历史

带来源周期的用例在回放时提供 `search_customer_history`，只检索同一客户在用例 `occurred_at` 之前关闭的周期，防止检索到被评测周期本身；手动用例不提供该工具。

## 5. 界面

- 用例侧栏与每次结果的评测时快照按客户、AI、真人区分展示前文，复用质检沟通记录的样式，负责人能看出 AI 在哪一步出错。
- 用例列表的次要信息标出来源（待补知识、问题会话）。

## 6. 验收

- 从待补知识和问题会话加入的用例，前文与提问按所选消息正确截断，原会话删除后用例仍可运行。
- 侧栏前文按客户、AI、真人区分发送方。
- 回放带来源周期的用例时，客户历史检索不返回被评测周期及其之后关闭的周期。
