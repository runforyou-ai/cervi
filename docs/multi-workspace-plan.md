# 多工作区与账号模型方案

状态：待评审
日期：2026-09-26
范围：部署级账号、多工作区、会话与工作区识别、注册与工作区创建、成员邀请、三端入口、自定义域名；自托管与官方托管共用
关联：本文取代 [官方托管服务建设方案](saas-hosting-plan.md) 中关于企业域名、租户解析、身份绑定、成员邀请和企业开通的设计，见第 13 节

## 1. 建设目标

一个 Cervi 部署承载多个工作区。账号属于部署，一个账号可以加入多个工作区，在各端登录一次后切换工作区。自托管与官方托管使用同一套账号、工作区和成员模型，差别只在账号来源和权益来源。

- 各端连接部署地址并登录账号，按账号列出可进入的工作区。桌面端和移动端始终连接部署地址，不按工作区切换服务器。
- Web 端默认通过部署地址访问工作区；工作区可以绑定自定义域名，用于 Web 访问、对外访客页面和 Webhook。
- 成员只通过邀请加入工作区；管理员不再直接创建带密码的成员。
- 产品文案统一使用「工作区」，代码中的 organization 模型保留原名。

## 2. 术语

| 术语 | 含义 | 代码对应 |
| --- | --- | --- |
| 部署 | 一套 cervi-server 及其数据库、NATS 和文件存储 | 部署配置 |
| 部署地址 | 部署的公开 HTTPS 地址，各端连接和 Web 访问的默认入口 | 新增 `server.publicURL` |
| 账号 | 部署内唯一的登录主体，按邮箱唯一 | 新增 `accounts` |
| 工作区 | 数据隔离单位，所有业务数据按工作区编号隔离 | `organizations` |
| 成员 | 账号在某个工作区中的身份，承载角色、团队、接待设置和工作区内展示资料 | `users` 加 `organization_identities` |
| 部署管理员 | 首次安装时创建的账号，承担后续部署级管理能力 | `accounts.is_deployment_admin` |
| 自定义域名 | 已验证归属并绑定到某个工作区的域名 | 新增 `organization_domains` |

## 3. 两种部署形态

| 能力 | 自托管 | 官方托管 |
| --- | --- | --- |
| 账号来源 | 本地账号：邮箱加密码 | 官方身份服务（OIDC），首次登录时创建账号 |
| 账号注册 | 部署配置 `deployment.registrationOpen`（`REGISTRATION_OPEN`）控制是否开放注册，默认关闭；关闭时只能凭邀请注册 | 在官方身份服务注册 |
| 首次安装 | Web 初始化页创建部署管理员账号和第一个工作区 | 不提供初始化页 |
| 创建工作区 | 任何已登录账号 | 任何已登录账号，受账号的免费工作区数量上限约束 |
| 密码登录与修改密码 | 提供 | 不提供 |
| 成员加入 | 邀请 | 邀请 |
| 自定义域名 | 支持 | 支持 |

部署形态仍由 `deployment.mode` 区分。托管部署额外配置官方身份服务；自托管部署的全部能力不依赖官方服务。

## 4. 数据模型

### 4.1 账号

`accounts`：

| 字段 | 含义 |
| --- | --- |
| id | 账号编号 |
| email | 登录与联系邮箱，按 `lower(email)` 全部署唯一 |
| email_verified_at | 邮箱验证时间，为空表示未验证 |
| password_hash | 本地密码摘要，托管账号为空 |
| display_name | 账号名称，加入工作区时作为成员显示名称的默认值 |
| locale、time_zone | 账号语言与时区 |
| status | active、inactive；停用后不能登录 |
| is_deployment_admin | 是否为部署管理员 |

`account_external_identities`：账号与官方身份服务账号的绑定，`(issuer, subject)` 唯一，`(account_id, issuer)` 唯一。

### 4.2 成员

`users` 表示成员，新增 `account_id`，`(organization_id, account_id)` 唯一。

| 字段 | 归属 | 说明 |
| --- | --- | --- |
| email、password_hash | 移到 `accounts` | 成员展示账号邮箱，登录凭据只属于账号 |
| locale、time_zone | 移到 `accounts` | 个人偏好跨工作区一致 |
| role_id、status、max_service_sessions、last_service_assigned_at、translation_language、message_notifications_enabled、profile_version、pin_order_version | 保留在 `users` | 按工作区设置 |
| 显示名称、头像、工作状态、接待开关 | 保留在 `organization_identities` | 按工作区设置 |

成员停用只影响该工作区；账号停用使该账号在所有工作区都不能登录。

原 `external_identities`（按工作区绑定官方身份）由 `account_external_identities` 取代。

### 4.3 工作区与域名

- `organizations.access_host` 删除，新增 `slug`：工作区标识，全部署唯一，用于 Web 地址，规则为 1 到 63 位小写字母、数字或连字符，首尾不是连字符。创建时按名称生成，名称无法转成标识时生成随机标识；创建后不修改，是否开放修改及旧链接如何跳转见第 16 节。
- `organization_domains`：`host` 全部署唯一，`organization_id`，`verification_token`，`verified_at`。验证通过的域名参与工作区识别，一个工作区可以绑定多个域名。

### 4.4 会话与登录尝试

- `account_sessions`：`account_id`、`token_hash`（唯一）、`client_type`（web、desktop、mobile）、`expires_at`。会话令牌只标识账号，不绑定工作区。
- 原 `tokens` 表由 `account_sessions` 取代。
- `login_attempts` 删除 `organization_id`，新增可空的 `invitation_id`；用途为 `login` 或 `accept_invitation`，客户端类型为 `web`、`desktop` 或 `mobile`。

### 4.5 成员邀请

`organization_invitations`：`organization_id`、`invited_email`（规范化存储）、`role_id`、`display_name`（为空时加入后使用账号名称）、`token_hash`（唯一）、`status`（pending、accepted、revoked、expired）、`expires_at`、`invited_by_user_id`、`accepted_user_id`、`accepted_account_id`、`accepted_at`。同一工作区同一邮箱在 pending 状态下唯一。

## 5. 会话与工作区识别

### 5.1 账号登录

- 自托管：邮箱加密码登录账号，签发账号会话令牌。
- 官方托管：官方身份服务登录，完成授权码交换后按 `(issuer, subject)` 找到或创建账号，签发账号会话令牌。首次登录创建账号时，邮箱与验证状态取自 ID Token。
- 登录不需要选择工作区。登录后调用 `ListMyWorkspaces` 取得该账号的有效成员身份列表。

### 5.2 请求的工作区

工作区级接口的请求携带账号会话令牌和目标工作区，服务端按以下顺序确定工作区：

1. 访问地址是已验证的自定义域名：工作区由域名确定；请求显式给出的工作区必须与之一致。
2. 其他访问地址：使用请求显式给出的工作区编号，缺少时返回需要选择工作区的会话状态。

确定工作区后，按「账号会话 → 账号 → 该工作区中的有效成员」解析身份。账号在该工作区没有成员身份、成员已停用或账号已停用时，请求被拒绝。现有 Action 继续接收已解析的工作区与成员身份，业务查询按工作区编号隔离的方式不变。

账号级接口（账号资料、工作区列表、创建工作区、接受邀请、部署设置）只需要账号会话。

`RequestMeta` 新增 `workspaceID`，HTTP 通过 `X-Cervi-Workspace` 请求头传输。

### 5.3 退出与停用

- 退出登录删除当前账号会话。
- 账号停用时删除该账号的全部会话；修改密码时删除除当前会话外的全部会话。被删除会话在各工作区的实时连接随之关闭。
- 成员停用不删除会话，该工作区的请求按成员状态拒绝。

## 6. 注册、首次安装与工作区创建

### 6.1 首次安装（自托管）

部署中没有账号时，Web 端进入初始化页，填写账号名称、邮箱、密码、工作区名称和工作区标识，事务内创建部署管理员账号、第一个工作区、内置角色和该账号的管理员成员身份。已有账号后初始化入口关闭。

### 6.2 账号注册

- 自托管：部署配置开放注册时登录页提供注册入口；关闭时只能通过邀请链接注册，注册邮箱须与受邀邮箱一致。部署尚未完成首次安装时不接受注册，第一个账号只能由首次安装创建。首期不提供邮箱验证流程，注册后账号邮箱为未验证，通过邀请加入工作区时标记为已验证，见第 7 节。
- 官方托管：不提供本地注册，账号在官方身份服务注册。

### 6.3 创建工作区

任何已登录账号都可以创建工作区，创建者成为该工作区的管理员成员。事务内创建工作区、内置角色和创建者成员身份，复用现有的企业默认数据创建能力。托管部署在创建前检查账号的免费工作区数量上限，见第 11 节。

## 7. 成员邀请

- 工作区成员在成员管理页发起邀请，填写受邀邮箱、角色和显示名称（选填），得到邀请链接。邀请令牌只保存摘要，明文只在创建时返回一次。首期由发起人复制链接转达；部署配置了邮件发送时同时在后台投递邀请邮件，界面只说明邮件正在发送，投递结果不回传。
- 成员管理页的账号状态筛选提供「待接受」，列出 pending 邀请（含已过期未处理的），可以重新生成链接或撤销。
- 邀请链接为 `<访问地址>/#/invitations/<令牌>`。令牌位于片段中，不进入服务端访问日志和 Referer。
- 受邀人打开链接后看到工作区名称、邀请人和掩码后的受邀邮箱（保留首字符和域名，其余固定为三个星号，不暴露长度）；令牌不存在、已撤销、已接受或已过期时统一展示链接失效。未登录时先登录或注册，注册入口在邀请页始终可用，不受注册开关限制；登录或注册完成后回到邀请页，由受邀人确认加入。
- 接受在单个事务中完成：锁定邀请并校验为 pending 且未过期；锁定账号，按事务内的当前邮箱判断；账号已是该工作区成员时拒绝并提示直接进入该工作区；校验账号邮箱与受邀邮箱一致（不区分大小写）；按邀请的角色创建成员身份，角色已删除时邀请失效；邀请置为 accepted；账号邮箱未验证时标记为已验证。
- 凭邀请注册时，注册事务以共享锁读取邀请并校验注册邮箱与受邀邮箱一致，撤销或重新生成与注册串行执行。
- 邮箱验证要求：官方托管要求官方身份的邮箱已验证。自托管首期以邀请令牌加邮箱一致为准，不做单独的邮箱验证流程：持有发往该邮箱的邀请链接并以同一邮箱的账号接受，视为邮箱已验证。配置邮件发送后是否在注册时要求验证邮箱见第 16 节。
- 邀请有效期 7 天。邀请可以撤销；「重新生成链接」撤销原邀请并以相同内容创建新邀请，原链接立即失效。对同一邮箱重新邀请时，事务内先把该邮箱已过期的 pending 记录置为 expired。
- pending 邀请（含已过期未处理的）与成员一样占用角色，撤销后该角色才能删除。
- 管理员直接创建成员的 `CreateUser` 删除，两种部署只有邀请一条成员加入路径。

## 8. 三端入口

### 8.1 Web

- 部署地址下的路由：`/#/login`、`/#/register`、`/#/setup`、`/#/workspaces`（工作区列表与创建），工作区内页面为 `/#/w/<工作区标识>/<页面>`。
- 打开部署地址时，已登录账号进入最近使用的工作区；没有可进入的工作区时进入工作区列表，提供创建入口。
- 自定义域名下的路由与现在相同（`/#/inbox` 等），工作区由域名确定。
- 工作台左上角提供工作区切换器，列出账号的全部工作区，并提供创建工作区入口；托管部署另外提供账号与订阅入口。
- 账号会话令牌保存在 `localStorage`；多个工作区共用同一个令牌，切换工作区只改变请求中的工作区。

### 8.2 桌面端与移动端

- 连接页填写部署地址。官方托管版客户端内置官方部署地址，用户可以改为自托管地址。
- 连接后按部署探测结果展示登录方式：自托管为邮箱密码登录和注册入口（按注册开关）；官方托管为系统浏览器中的官方身份授权。原生端授权回调使用部署地址下的声明式链接（iOS Universal Links、Android App Links），声明文件由部署地址提供。
- 登录后选择工作区，之后在工作台切换；移动端在「我的」页进入工作区列表切换。本地保存部署地址和账号会话，账号会话不记录当前工作区，每个请求自行携带目标工作区，多个窗口可以分别停留在不同工作区；最近使用的工作区由界面保存。
- 设备注册、推送和实时连接按「部署地址 + 账号 + 工作区」区分。桌面端在账号作为有效成员的每个工作区注册本机设备，账号不再是某工作区的有效成员时删除该工作区的本机注册结果；领取运行、设备事件流和本机 Agent 上报同时覆盖这些工作区，助理不受当前打开的是哪个工作区影响。打开尚未注册的工作区时立即注册。
- 登录、退出或切换服务器后，桌面端关闭上一会话打开的会话独立窗口。
- 其他工作区的消息提醒、通知点击后进入对应会话，以及推送中继不在阶段三范围内。

### 8.3 部署探测

`GET /installation/status` 改为部署探测，返回部署名称、部署形态、是否已完成首次安装、支持的登录方式和是否开放注册，不返回工作区信息。自定义域名下额外返回该工作区名称与标识。

## 9. 对外访客、Webhook 与链接

- 对外访客页面、挂件和 Webhook 按路径中的渠道编号确定工作区，与访问地址无关。签名客户身份的本地文件上传同样改为按渠道确定工作区。
- 服务端生成的绝对链接（客户续聊链接、Agent 附件地址、邀请链接）优先使用工作区已验证的自定义域名，没有时使用部署地址。
- 对象键仍为 `organizations/<工作区编号>/...`；本地文件内联读取按对象键中的工作区编号确定内容类型。

## 10. 自定义域名

- 工作区管理员在工作区设置中添加域名，服务端生成 TXT 验证记录；用户添加 DNS 记录后发起验证，验证通过后写入 `verified_at`。同一域名只能被一个工作区验证。
- 证书：`TLS_MODE=auto` 时按已验证的自定义域名和部署地址申请证书，取代现有按企业访问地址放行的规则；`TLS_MODE=external` 时由前置入口负责证书。
- 官方托管部署中，已验证的自定义域名的 Web 登录回调追加到官方身份服务的 Web 客户端；部署地址的回调在部署时登记一次。
- 删除域名后，该域名不再参与工作区识别和链接生成。

## 11. 官方托管与商业化边界

### 11.1 官方托管

- 官方身份服务按账号接入：`login` 用途完成后签发账号会话，`accept_invitation` 用途在同一次交换中完成接受邀请。授权码交换、PKCE、nonce 与 ID Token 校验沿用现有实现，回调地址为部署地址或工作区自定义域名。
- 工作区在 Cervi 内创建。订阅按工作区计费（套餐加席位），由工作区管理员账号付费；权益由 SaaS 按工作区同步到 `organization_entitlements`，沿用现有的权益版本与对账机制。账号只受免费工作区数量上限约束，上限由 SaaS 按账号下发。无效权益下的工作区按现有生命周期规则限制使用。
- SaaS 承担官方账号、订阅与账单，不再承担开通流程；官网提供进入部署地址的入口。运营 API 的开通接口改为按工作区的权益同步与按账号的免费工作区上限同步，具体契约在托管阶段实施前确定。
- 托管部署关闭密码登录、修改密码和本地注册。

### 11.2 统一权益

席位上限、功能开关、AI 额度和有效期都通过同一个权益结构检查，两种部署只有权益来源不同：

| 来源 | 适用 | 内容 |
| --- | --- | --- |
| 默认权益 | 自托管 | 席位不限，开源功能全部可用，企业功能关闭 |
| 授权文件 | 自托管企业版 | 官方私钥签名，服务端用内置公钥离线校验，打开对应企业功能并给出有效期 |
| SaaS 同步 | 官方托管 | 按工作区的套餐快照 |

### 11.3 商业化边界

- 代码保持 Apache 2.0。核心业务功能（收件箱、渠道、成员、多工作区、AI 助理框架）在两种部署中完整可用，两种部署不以功能删减区分。
- 官方托管收入：工作区订阅；内置 AI 模型额度，超出部分按量计费；运维、备份、邮件、对象存储、证书和服务承诺包含在订阅中。
- 自托管收入：企业功能授权（SAML 单点登录、审计日志、细粒度权限、数据保留策略、部署级管控、高可用部署支持）和私有化实施与支持合同。企业功能同为 Apache 2.0，授权文件用于商业交付与支持，不作为技术保护手段。
- 移动端推送：官方发布的移动端使用官方推送证书，自托管部署向官方移动端推送经官方推送中继，免费额度内可用，企业授权或托管订阅不限量；自行构建移动端的部署使用自己的推送证书，不经过中继。
- 官方桌面端与移动端的同一个安装包既能连接官方托管，也能连接任意自托管部署。

## 12. 安全边界

- 每个工作区级请求都校验「账号会话 → 成员身份 → 工作区」关系，这是工作区隔离的核心边界，由服务端分发层统一执行，并用集成测试覆盖跨工作区访问。
- 部署地址下各工作区共用同一个 Web 来源，账号会话令牌对该账号的全部工作区有效。Web 端启用内容安全策略，用户内容渲染纳入上线前安全检查。
- 自定义域名只有验证通过后才参与识别和证书申请。
- 登录尝试一次性消费，按用途和客户端类型限定；邀请令牌只保存摘要。

## 14. 实施阶段

| 阶段 | 交付内容 | 完成标准 |
| --- | --- | --- |
| 一：账号与多工作区 | 账号、成员身份、账号会话、工作区识别、首次安装、注册开关、创建工作区、Web 工作区列表与切换器、文案改为工作区 | 自托管部署中一个账号创建并切换多个工作区，跨工作区访问被拒绝 |
| 二：成员邀请 | 邀请模型与接口、邀请页、注册与登录衔接、删除 CreateUser | 第二个账号通过邀请加入工作区并正常使用 |
| 三：原生端 | 连接部署地址、账号登录、工作区选择与切换 | 桌面端和移动端登录一次后在多个工作区间切换 |
| 四：官方托管 | 官方账号按账号登录、原生端系统浏览器授权、按工作区订阅与免费工作区上限、SaaS 调整 | 官方账号在 Web 与原生端登录并创建、切换工作区 |
| 五：自定义域名 | 域名验证、识别、证书、链接与回调 | 工作区通过自定义域名访问 Web 与对外访客页面 |

阶段一到三不依赖官方托管；SaaS 相关工作在阶段四之前暂停。

## 15. 验收要求

- 同一邮箱在部署内只能注册一个账号；一个账号可以是多个工作区的成员。
- 工作区级请求在账号没有该工作区成员身份、成员停用或账号停用时被拒绝；携带其他工作区编号的请求读不到当前工作区数据。
- 自定义域名下请求显式给出的工作区与域名不一致时被拒绝。
- 首次安装只能执行一次；关闭注册后只能通过邀请注册。
- 邀请按邮箱一致性、有效期、撤销和一次性接受规则执行；已是成员的账号不能重复加入。
- 切换工作区不需要重新登录；退出登录后所有工作区的请求都被拒绝。
- 对外访客页面与 Webhook 在部署地址和自定义域名下都能按渠道工作。
- 托管部署不提供密码登录、修改密码和本地注册。
