# Cervi 客户身份与业务系统接入方案

状态：设计中  
日期：2026-09-23  
范围：网站 Messenger 登录用户识别、访客上下文、AI 通过 MCP 查询业务系统并作为回答依据  
关联：本文是 [Cervi 路线图](roadmap.md) 登记的独立方案，对应「客服运营与渠道」中的业务系统接入（P1）、登录用户识别（P1）与访客上下文（P1），设计细节只保留在本文

本文是主要参考，不构成强制约束，实施中按更合适的做法调整并同步更新；已交付的部分以代码为准，全部交付后连同路线图中的对应条目一并删除。

## 目标

客户在企业网站登录后打开 Messenger，AI 员工知道他是谁，能查询他自己的订单、账户等记录，并依据查询结果直接答复；查询失败或客户未登录时追问或转人工。客服接手时在侧栏看到客户身份、本次访问上下文和 AI 查过的业务数据。

验收场景：

- 企业把内部订单系统包装成 MCP 服务，登录用户问「我的订单到哪了」，AI 调用查询工具取得该用户的订单并作答，全程不转人工。
- 登录用户没有订单时，AI 依据空结果答复「没有查到订单」，不转人工。
- 匿名访客问同样的问题，AI 通过 `ask_customer` 引导登录，或转人工。

## 现状

- 网站访客完全匿名：服务端签发随机访客 Token，渠道身份的外部编号为 `web-session:<token>`，挂件没有传入已登录用户的接口。
- MCP 服务配置、AI 员工绑定和运行时挂载工具已具备；运行时挂载服务发现到的全部工具，MCP 工具报错（`IsError`）时调用按失败返回。
- 客服场景使用严格依据策略：直接输出的正文必须取得依据，否则纠正一次后按 `insufficient_evidence` 转人工；`ask_customer`、转人工与结束会话不经过该门禁。依据来源只登记了知识检索。
- 显示名称按「渠道身份名称优先，其次联系人名称」读取。
- 客服侧栏的「业务」页签是占位。

## PR 1：登录用户识别与访客上下文

### 客户身份密钥

- 客户身份密钥是企业级设置，所有网站渠道共用；企业用户编号在企业内是同一套编号体系。不变量：同一企业的所有网站使用同一套用户编号，不同网站的同一编号即同一客户。
- 密钥为 32 字节随机值，以 base64url 字符串展示；签发与验签都以该字符串的 UTF-8 字节作为 HMAC 密钥。
- 管理员在设置中查看、复制和重新生成密钥。重新生成立即生效、没有重叠期：已登录客户的下一次请求会身份失效，网站须在重新生成后更新配置。重新生成前使用 `ConfirmationDialog` 说明这一影响。
- 已接受的风险：角色权限建设前任何成员都能看到密钥，即能以任意客户身份访问 Messenger，PR 2 后还能据此查询该客户的业务数据。随角色权限统一收口。

### 签名身份

企业网站服务端签发 JWT，服务端校验规则：

| 项 | 规则 |
|---|---|
| 算法 | 只接受 HS256，拒绝 `none` 与其他算法 |
| `sub` | 必填，企业用户编号；1–128 个字符，只允许字母、数字和 `-_.:@`，拒绝空白与控制字符 |
| `exp` | 必填；`exp - now` 不超过 24 小时，超过即拒绝 |
| `iat` | 可选 |
| 时钟偏差 | 允许 60 秒 |
| `name` | 可选，显示名称，最长 128 个字符 |
| `email` | 可选，邮箱，格式非法时忽略该字段 |

- 身份失效（签名无效、过期、超出有效期上限）使用独立的稳定错误码，与访客 Token 非法区分。
- 设置页先给出一个规范样例（Node），多语言示例在字段和规则定稿后补充。

### 挂件接口

- 一个页面只嵌入一个网站渠道挂件。
- 页面加载时已登录的，在加载脚本前设置 `window.cerviSettings = { customerToken }`，挂件首次初始化即以该身份进行。
- `window.Cervi.login(token)`：切换到该用户，已登录时直接替换当前用户。
- `window.Cervi.logout()`：回到匿名访客，并轮换匿名访客 Token，不恢复登录前的匿名会话。
- `window.Cervi.on("identityExpired", callback)`：身份失效时通知宿主，宿主重新签发后调用 `login()`。
- 宿主集成约束：客户在调用 `login()` 之前发出的消息属于匿名会话，登录后不并入。

签名身份的传递：

- 挂件保存当前签名身份，通过 `postMessage` 以 Cervi 源作为 `targetOrigin` 下发给聊天页，并在 `cervi:frame-ready` 时重新下发；聊天页只接受 `event.source === window.parent` 的身份消息。
- 聊天页在内存中保存签名身份，每个公开请求以 `X-Cervi-Customer-Token` 请求头携带，覆盖初始化、消息、会话目录与历史、输入状态、评价、附件上传与下载、实时连接的全部公开入口。签名身份不写入 Cookie 与 `localStorage`。
- 聊天页向父页面发送消息时使用嵌入时确定的父源，父源未知时不发送，不使用 `*`。

身份切换与失效：

- 登录、退出、切换用户和身份失效时，聊天页递增身份代次：关闭实时连接，中止进行中的请求与附件上传，清空会话目录、消息窗口和草稿，之后以新身份重新初始化；旧代次请求的晚到响应一律丢弃。
- 身份失效时，Messenger 显示登录已过期并禁用输入，同时触发 `identityExpired`；宿主调用 `login()` 或 `logout()` 后恢复。失效时发送失败的消息不以匿名身份重发。
- 实时连接在签名身份的 `exp` 到达时由服务端关闭；密钥重新生成时，服务端关闭该企业全部以签名身份建立的实时连接。
- 验签通过的初始化不轮换匿名 Cookie，退出后仍使用新轮换的匿名 Token。
- 验收覆盖：目录请求在途时切换账号、附件上传中切换账号、实时连接建立后身份过期。

### 服务端验签与身份映射

- 公开入口先读签名身份：验签通过时渠道身份的外部编号为 `web-user:<sub>`，匿名访客 Token 不参与；缺少签名身份时沿用匿名 Token。
- 同一用户在多个浏览器与设备上共用同一个渠道身份，看到同一份会话列表。同一 `sub` 在不同网站渠道对应同一联系人、各自的渠道身份，会话列表按渠道分开。
- 验签通过的第一次公开请求（含初始化）即确保渠道身份与联系人存在，AI 首轮运行就能取得客户身份。

### 联系人关联

- 联系人增加企业用户编号字段，唯一范围为企业内全部联系人（包括已软删除的），与渠道身份恢复软删除联系人的规则一致。
- 查找或新建联系人时以唯一约束处理并发：插入冲突后重读。
- 签名中的 `name` 写入该渠道身份的显示名称，与 Telegram 资料名称同一语义；省略时不清空。联系人自身的显示名称由客服维护，签名不写入，现有的显示名称读取规则不变。
- 签名中的 `email` 在联系人没有该邮箱时添加为联系方式，联系人没有主邮箱时设为主邮箱；不覆盖、不删除已有邮箱，不按邮箱合并联系人。省略时不改动。
- 联系人阶段保持访客，不因验证身份而改变。
- 已验证只表示签名身份校验通过，不代表邮箱所有权。客服侧栏「资料」页签展示已验证标记、企业用户编号和邮箱。

### 访客上下文

访客上下文按客服周期保存，同一用户多设备同时访问时互不覆盖：

| 信息 | 采集方式 | 保存规则 |
|---|---|---|
| 来源页 | 宿主页 `document.referrer` | 客服周期开始时记录，常为空，为空时侧栏留空 |
| 当前页 | 宿主页 URL 的源与路径及页面标题；挂件监听前进后退、`pushState`、`replaceState` 与 `hashchange` | 随该周期的每条访客消息更新，先写入再触发 AI 运行 |
| 设备 | User-Agent 解析为浏览器、操作系统与设备类型 | 随该周期的每条访客消息更新 |
| 语言与时区 | 浏览器首选语言与时区 | 随该周期的每条访客消息更新 |
| 地区 | 部署配置指定的可信代理国家头（如 `CF-IPCountry`） | 随该周期的每条访客消息更新；部署须保证反向代理覆盖客户端同名头，未配置时不采集 |

- URL 在采集时去掉查询串和 hash。
- 客服侧栏「资料」页签展示当前周期的访客上下文。
- 客服场景的 AI 上下文注入：客户是已验证用户还是匿名访客、名称、当前页、语言与地区。不注入企业用户编号、邮箱和签名身份。
- 回复语言仍以客户最近一条消息为准，浏览器语言只在无法判断时作为后备；AI 翻译与多语言内置指令不在本方案范围。
- 本方案不完成路线图的「客户档案注入」：不注入备注、历史会话摘要和联系方式。

## PR 2：业务系统查询作为回答依据

### 工具用途

- MCP 服务的每个工具由管理员标记用途：查询或操作；新发现的工具未标记。标记按「服务 + 工具名」保存，刷新工具目录后保留仍存在的工具的标记，工具改名视为新工具。
- 客服场景只挂载标记为查询的工具；操作与未标记的工具在客服场景不挂载，随「P1.5：服务端副作用、审批和恢复」开放。其他场景的挂载规则不变。
- 查询工具即客服场景的依据来源，不另设依据开关。标记为查询是管理员对只读性的承诺，运行时不校验工具实际行为。

### 依据判定

- 查询工具调用成功且未标记错误时，结果即依据，包括空列表、空对象等「没有记录」的结果；结果去除空白后为空、传输失败或 `IsError` 不构成依据。
- 查询工具使用独立的判定函数，不复用知识检索的判定。
- 大结果被截断或清理后，沿用现有规则：模型完整读回原始结果才构成依据。
- 需要客户补充信息时仍使用 `ask_customer`。

### 客户范围服务

- MCP 服务增加「按客户查询」开关，服务级生效；同一服务不能同时提供公开查询与客户数据查询，需要时拆成两个服务。
- 开启后，客服场景的运行建立该服务会话时，在每个 HTTP 请求上附加 `X-Cervi-Customer-Id`（签名身份的 `sub`），有邮箱时附加 `X-Cervi-Customer-Email`。客户头在建立会话时固定，本次运行内不变。
- 客户已验证的定义：当前客服周期的渠道身份外部编号为 `web-user:<sub>` 且联系人有企业用户编号。未验证时该服务的工具不挂载；场景规则告知 AI 客户尚未登录，涉及个人数据的问题通过 `ask_customer` 引导登录，或转人工，不直接输出正文。匿名期间开启的客服周期在客户登录后仍为匿名，始终不挂载客户范围工具。
- 连接测试与工具目录刷新不附加客户头；业务系统在没有客户头时须仍能返回工具目录。
- 业务系统须以请求头确定数据范围：忽略工具参数中的客户编号，并校验订单号等资源属于该客户。邮箱头只作参考，不能作为授权依据。Cervi 以 MCP 认证令牌向业务系统证明调用方，不保证业务系统内的数据隔离。
- 设置页在开关旁用一行帮助文案说明请求头名称与业务系统须遵守的规则。

### 客服侧栏「业务」页签

- 列出当前客服周期内客服 AI 运行调用查询工具的全部记录：工具名称、查询参数、结果与时间，标出构成依据的调用，失败的调用展示失败说明；按时间倒序。不包含客服侧 AI 助手的运行。
- 数据来自运行过程记录，不另存副本：运行进入终态后才可见，保留期与运行过程记录一致。
- 过程记录中被截断的大结果只展示已记录的预览并标注已截断；JSON 结果格式化展示，超过展示上限时折叠。

## 暂不包含

- 匿名身份并入登录用户。
- Telegram 等其他渠道的客户身份验证：出现需求时按渠道单独设计，复用企业级客户身份密钥与企业用户编号。
- 客服在侧栏主动调用业务系统。
- 按 IP 解析地区的内置地理库。
- 密钥轮换重叠期：出现网站无法接受身份中断的反馈时增加。
